# Feuille de route v3.2 — DevForge pour tout le monde

**Cap** : maintenant que DevForge est public, un nouveau venu doit pouvoir le comprendre, le configurer et y contribuer seul ; et le logiciel doit pouvoir sortir de Windows.
**Base** : v3.1.0 (menu qui attend un serveur pour lister les pages qui en demandent un, projet mobile abandonné, docs rangées).

## Vue d'ensemble

| Lot | Contenu | Taille |
|---|---|---|
| 1 | Clôturer la v3.0 : parcours d'un inconnu sur un profil vierge | S |
| 2 | L'aide dans l'appli : chaque page renvoie vers sa documentation du site | M |
| 3 | Connexions complètes : n8n et alertes ntfy | S |
| 4 | Contribuer facilement : modèles d'issue et de PR, sécurité, premières tâches | S |

Taille : S ≈ 1 à 2 sessions, M ≈ 3 à 5, L ≈ 6 et plus.

## Lot 1 — Clôturer la v3.0

Le lot 6 de la v3.0 : installer la version publique sur un profil Windows vierge et dérouler les 7 étapes de [v3.0.md](v3.0.md#lot-6--vérification-sur-une-installation-vierge). Chaque écart trouvé devient un correctif.

**Fini quand** les 7 étapes passent sans aide extérieure.

## Lot 2 — L'aide dans l'appli

Le site (téléchargement et documentation détaillée, construit à part) donne une page par fonction. L'appli y renvoie :
- un bouton « ? » dans l'en-tête de chaque page, vers sa page de documentation, dans la langue de l'interface ;
- le premier lancement et les pages « à configurer » renvoient vers la prise en main ;
- les notes de version renvoient vers la page « Quoi de neuf » du site ;
- l'adresse du site se lit dans `package.json` (`homepage`), comme celle du dépôt : un fork pointe vers sa propre doc.

**Fini quand** chaque page listée dans le menu mène à une page de doc qui existe (vérifié par un test qui parcourt `navigation.ts`).

**Fait** :
- adresse du site dans `package.json` (`homepage`), injectée au build (`__DOCS_URL__`) comme celle du dépôt ; sans elle, aucun lien d'aide ne s'affiche ;
- chaque page de `navigation.ts` porte sa page de doc (`docs`), les pages de détail comptent pour leur parent (fiche projet → Projets, serveur → SSH) ;
- bouton « ? » dans la barre de titre (plutôt que dans l'en-tête de chaque page : un seul endroit, toujours visible) et touche **F1** : la doc de la page affichée, en français ou en anglais selon l'interface ;
- premier lancement : « Lire la prise en main sur le site » ; pages « à configurer » : « Comment faire » vers la page Connexions de la prise en main ;
- tests : `tests/renderer/docsLinks.test.ts` vérifie que chaque page a sa doc dans `site/src/content/docs/`, en français et en anglais ; `tests/e2e/lot32-2.e2e.ts` vérifie les boutons (sans cliquer : ça ouvrirait le navigateur).

**Reste** : le lien des notes de version vers une page « Quoi de neuf » du site, qui n'existe pas encore ; et une ligne sur le bouton « ? » et F1 dans la page « Interface » du site.

## Lot 3 — Connexions complètes

Le reste du lot 1 de la v3.0 : n8n (adresse, clé API) et les alertes ntfy (sujet, serveur) se règlent, se testent et se retirent aussi depuis Paramètres › Connexions, et plus seulement depuis leur page.

**Fini quand** Connexions liste tous les services que DevForge peut joindre.

**Fait** (carte « n8n et alertes » de Connexions) :
- n8n : chaque instance installée depuis DevForge, avec son serveur et son adresse ; clé API à saisir, tester (le nombre de workflows), retirer ; lien vers la page n8n ;
- alertes de la page de statut : elles vivent sur le serveur, donc lues à la demande (« Lire les alertes », par SSH) pour garder la section rapide ; état ntfy (et webhook), sujet et serveur ntfy à régler, test (le même envoi qu'une vraie panne), retrait ; le sujet n'est jamais réaffiché (qui le connaît reçoit les alertes) ; un sujet ou un serveur refusé l'est avant tout envoi au serveur ;
- tests : `tests/main/lot32-3.test.ts` et `tests/e2e/lot32-3.e2e.ts` (réponses du serveur simulées).

L'installation de n8n et de la page de statut reste sur leur page : elle demande des choix (domaine, exposition) qui n'ont pas leur place dans Connexions.

## Lot 4 — Contribuer facilement

- Modèles d'issue (bug, idée) qui demandent le rapport de diagnostic (Paramètres › À propos), et un modèle de pull request qui rappelle `npm run check`.
- `SECURITY.md` : signaler une faille en privé (onglet Security de GitHub).
- La CI d'une pull request venue d'un fork tourne sans le secret `PERSONAL_PATTERNS` : vérifier qu'elle passe quand même (le garde-fou se saute), et le dire dans `CONTRIBUTING.md`.
- Quelques issues « good first issue » prêtes, tirées de cette feuille de route.

**Fini quand** une personne extérieure peut ouvrir une issue utile ou une PR qui passe la CI sans rien demander.

## Lot 5 — macOS et Linux

DevForge ne tourne aujourd'hui que sous Windows : 17 tests de plateforme et une douzaine de services propres à Windows (ports, fichier hosts, terminal cmd et PowerShell, détection des bases, scripts de la page de statut…).
1. **Étude** : la liste de ce qui marche déjà ailleurs, de ce qu'il faut adapter, et de ce qui reste Windows seulement (masqué ailleurs, comme les pages qui attendent un serveur).
2. **Portage** : services adaptés derrière une interface par système, builds `.dmg` et `.AppImage` dans le workflow Release, CI sur les trois systèmes.

**Fini quand** l'étude est validée ; le portage peut glisser en v3.3 selon elle.

## Lot 6 — Mises à jour plus légères

- Vérifier que le téléchargement différentiel (blockmap) marche entre deux versions publiques (3.1 → 3.2) ; le passage 2.4 → 3.0 a téléchargé l'installeur entier, à cause du changement de dépôt.
- Régler l'avertissement `disableWebInstaller` d'`electron-updater`.

**Fini quand** une mise à jour ne télécharge que ce qui a changé.

## Lot 7 — Défauts vus en passant

Relevés en préparant le site ; petits, mais visibles par tout nouveau venu :
- le tableau de bord d'un serveur (`src/renderer/src/features/ssh/vps/`) garde des libellés en français quand l'interface est en anglais ;
- les dates de la fiche projet restent au format français en anglais : elles doivent suivre la langue de l'interface ;
- les descriptions des modèles de Nouveau projet (`src/shared/data/projectTemplates.ts`) sont en anglais en dur, même en français : elles passent dans `i18n/locales/fr.ts` et `en.ts` ;
- le panneau de Forgy demande une clé alors que `ANTHROPIC_API_KEY` existe : l'assistant sait s'en servir, mais l'état « clé présente » (`assistantStorage.ts`) ne regarde que la clé enregistrée ; Connexions doit aussi dire d'où vient la clé.

**Fini quand** l'interface ne mélange plus les deux langues sur ces pages (un test par page dans les deux langues), et que Forgy marche sans écran de clé quand `ANTHROPIC_API_KEY` est définie.

**Fait** :
- tableau de bord d'un serveur : ses 17 textes passent dans les traductions (`vpsDash`), l'uptime s'écrit « 3j » ou « 3d », l'heure de mise à jour suit la langue ;
- dates : Electron démarre dans la langue choisie dans DevForge (`--lang`), donc toutes les dates et nombres de l'appli la suivent (un changement de langue s'y applique au prochain démarrage) ; la fiche projet, le VPN et les migrations Symfony passent en plus la langue, et changent tout de suite ;
- Nouveau projet : descriptions des modèles et libellés des options dans les traductions ; les descriptions des 99 bibliothèques ont leur version française (`src/shared/data/projectLibraries.fr.ts`), recherche comprise ;
- Forgy : `ANTHROPIC_API_KEY` compte comme une clé (`keySource: 'env'`) ; le panneau et le widget ne demandent plus de clé, Paramètres › Forgy et Connexions disent « clé lue dans ANTHROPIC_API_KEY » (sans bouton Retirer, une clé enregistrée la remplace), et le test de Connexions l'utilise ; le message sans clé renvoie vers Connexions ;
- tests : `tests/e2e/lot32-7.e2e.ts` (Nouveau projet en français, dates en anglais puis en français, Forgy avec la variable) et deux cas Vitest pour la source de la clé.

Le tableau de bord d'un serveur n'a pas de test de bout en bout : il lui faut un vrai serveur SSH.
