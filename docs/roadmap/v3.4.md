# Feuille de route v3.4 — Un projet qui démarre prêt

**Cap** : un projet créé par DevForge s'ouvre sur sa propre page d'accueil, pas sur celle du framework ; avec l'option Authentification, on peut déjà s'inscrire, se connecter et appeler une API protégée, quel que soit le framework.
**Base** : v3.3.1.

## Vue d'ensemble

| Lot | Contenu | Taille |
|---|---|---|
| 1 | Page d'accueil DevForge, pour chaque framework | M |
| 2 | Le contrat d'API d'authentification, commun à tous | S |
| 3 | Auth Next.js (Auth.js, Prisma) | M |
| 4 | Auth Laravel (Fortify, Sanctum) | M |
| 5 | Auth Symfony (security, entité User) | M |

## Lot 1 — Page d'accueil DevForge

Une case **« Page d'accueil DevForge »**, cochée par défaut, à l'étape options de la création. Décochée, le projet garde la page du framework.
- Une seule identité visuelle pour tous : nom du projet, framework et version, ce que DevForge a mis en place (base, API, auth, Docker, tests, CI), liens utiles (doc du framework, route de santé, page de connexion si l'auth est là).
- La page ne dépend d'aucune bibliothèque ajoutée : CSS dans la page (Tailwind seulement quand le projet l'a déjà).
- Où elle s'écrit :
  - Next.js : `{app}/page.tsx` (et le titre dans `layout.tsx`) ;
  - React / Vue : `src/App.tsx` / `src/App.vue`, la feuille de style du modèle vidée ;
  - Symfony : `HomeController` sur `/` et `templates/home/index.html.twig` ;
  - Laravel : `resources/views/welcome.blade.php` ;
  - Node : `index.js` sert la page sur `http://localhost:3000` (module `http`, sans dépendance).
- Le résumé avant création montre les fichiers remplacés.

**Fini quand** chaque modèle, lancé une première fois, affiche la page DevForge avec ce qui a été réellement installé.

**Fait** (`src/shared/lib/welcomePage.ts`) :
- maquette retenue : B, « façon fiche projet » (canvas *DevForge — maquette 2.0*, rangée v3.4) : barre DevForge avec l'enclume orange, « Se connecter » et « Créer un compte » en haut à droite quand l'auth est choisie, colonne du projet (adresse, base, branche, étiquettes), tuiles « Ce qui est en place », liens « Pour continuer » ;
- sombre, comme l'app ; une seule source pour le JSX (Next.js, React), le composant Vue, le HTML (vue Blade, contrôleur Symfony sans Twig) et le serveur Node (module `http`) ;
- la page couvre toute la fenêtre (`position: fixed`) : les styles du modèle ne la gênent pas ;
- case dans la dernière étape de l'assistant, cochée par défaut ; le résumé montre les fichiers remplacés ;
- tests : `tests/main/welcome34.test.ts` (TSX lu par TypeScript, PHP par `php -l`, Node par `node --check`).

## Lot 2 — Le contrat d'API d'authentification

Les trois serveurs exposent les mêmes routes JSON, pour qu'un front React ou Vue marche avec n'importe lequel :

| Méthode | Route | Corps | Réponse |
|---|---|---|---|
| POST | `/api/auth/register` | `{ name, email, password }` | `201 { user }` |
| POST | `/api/auth/login` | `{ email, password }` | `200 { user, token }` |
| POST | `/api/auth/logout` | — | `204` |
| GET | `/api/auth/me` | en-tête `Authorization: Bearer <token>` (ou la session) | `200 { user }` / `401` |

- Erreurs : `422 { errors: { champ: [messages] } }` (validation), `401 { message }` (identifiants).
- Mot de passe : 8 caractères au moins ; jamais renvoyé ; haché par le framework (bcrypt / argon2).
- Le contrat est écrit une fois (`src/shared/data/authContract.ts`) et testé contre chaque modèle.
- Auth cochée sans base choisie : **SQLite** est pris automatiquement (pas de Docker), le résumé le dit.

**Fini quand** le contrat est décrit, partagé, et que la règle SQLite s'applique dans l'assistant de création.

**Fait** :
- `src/shared/data/authContract.ts` : routes, réponses, erreurs, règles (mot de passe de 8 caractères, bcrypt), pages `/login`, `/register`, `/dashboard`, variable `VITE_API_URL` ; la page d'accueil y lit ses liens ;
- jetons tranchés : Sanctum (en base) pour Laravel, JWT signé avec le secret du projet pour Next.js et Symfony ; le client ne voit qu'une chaîne opaque ;
- `withAuthDatabase` : auth sans base → SQLite, dans le plan comme dans l'assistant (un encadré le dit) ;
- tests : `tests/main/auth34.test.ts`.

## Lot 3 — Auth Next.js

- ~~Auth.js~~ : une auth maison sur le contrat (Auth.js ne rend pas de jeton à un client Bearer) : JWT signé avec `AUTH_SECRET` (`jose`), posé en cookie httpOnly pour les pages et rendu dans le JSON du login ; `bcryptjs` pour le hachage.
- Modèle `User` (id, name, email unique, passwordHash, createdAt) ajouté au schéma Prisma, première migration appliquée à la création.
- Routes du contrat sous `{app}/api/auth/…` (`register`, `login`, `logout`, `me`), `me` lit la session ou le jeton.
- Pages : `/login`, `/register`, `/dashboard` (protégée par le middleware, redirige vers `/login`).

**Fini quand** on s'inscrit, se connecte, voit `/dashboard`, se déconnecte, et que `/api/auth/me` répond 401 puis 200.

**Fait** (`src/shared/lib/nextAuthTemplate.ts`, projets TypeScript ; un projet JavaScript garde l'Auth.js minimal d'avant) :
- modèle `User` ajouté au schéma juste après `prisma init` (nouvelle étape « ajout », sans doublon), donc connu du client généré ; `prisma migrate dev --name init` une fois la base démarrée ;
- `lib/auth.ts` : hachage, jeton, `currentUser` (Bearer d'abord, puis le cookie), validation des règles du contrat, messages dans la langue de l'interface ;
- les quatre routes du contrat, `/login`, `/register` (inscrit puis connecte), `/dashboard` (redirige vers `/login`, montre l'API) avec la déconnexion ; même look que la page d'accueil ;
- tests : `tests/main/nextAuth34.test.ts` (TypeScript valide, une route par entrée du contrat, ordre des étapes).

Pas encore essayé sur un vrai projet créé.

## Lot 4 — Auth Laravel

- Fortify (déjà installé par l'option) : vues Blade de connexion et d'inscription, `/dashboard` protégé par `auth`.
- Sanctum : routes du contrat dans `routes/api.php`, jeton personnel au login, `HasApiTokens` (déjà posé).
- Avec Sail : tout passe par le conteneur, comme les migrations.

**Fini quand** les vues et les routes du contrat marchent, avec et sans Sail.

## Lot 5 — Auth Symfony

- Entité `User` (make:user, déjà dans l'option), `RegistrationController` et formulaire, `form_login` dans `security.yaml`, `/dashboard` protégé.
- Routes du contrat sous `/api/auth/…` : `json_login` pour le login, un jeton signé pour l'API (pare-feu `api` sans état).
- Première migration Doctrine appliquée à la création.

**Fini quand** l'inscription, la connexion par formulaire et les routes du contrat marchent sur un projet neuf.

## Lot 6 — Auth React / Vue

- Pages `Login`, `Register`, `Dashboard` et un petit client (`src/lib/auth.ts`) qui suit le contrat ; adresse du serveur dans `VITE_API_URL` (`.env.example`).
- Jeton gardé en mémoire et `localStorage`, envoyé en `Authorization: Bearer` ; `Dashboard` redirige vers `Login` sur un 401.
- Sans routeur dans le modèle Vite : un routage minimal par état, sans dépendance ; React Router ou Vue Router utilisés s'ils ont été choisis dans les bibliothèques.
- La page d'accueil (lot 1) dit à quel serveur le front s'attend et comment le lancer.

**Fini quand** un front React et un front Vue s'inscrivent et se connectent contre un projet Laravel, Symfony et Next.js créés par DevForge.

## Lot 7 — Documentation et vérification

- Vérifié sur de vrais projets : chaque modèle avec et sans page d'accueil, chaque serveur avec auth, React et Vue branchés sur un serveur.

**Fini quand** chaque nouveauté a sa page de doc dans les deux langues, et que les combinaisons ci-dessus passent.
