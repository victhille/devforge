# Feuille de route v3.8 — Suivre ses projets

**Cap** : DevForge aide à suivre ses projets au quotidien (ce qu'il reste à faire, ce qui a cassé sur GitHub, ce qui bouge ou dort), montre une base d'un coup d'œil, et fait partir un nouveau projet d'un de ses propres projets.
**Base** : v3.7.0.

## Lot 1 — Notes et tâches par projet

Un onglet **Notes** dans la fiche d'un projet (et dans le panneau d'un projet de groupe) :

- **Tâches** : une liste à cocher ; ajouter (Entrée), modifier (double-clic), supprimer, réordonner (glisser) ; **Masquer les faites** ; une tâche faite garde sa date.
- **Notes** : un bloc-notes en Markdown, enregistré au fil de la frappe, avec **Aperçu** (le même rendu que l'aperçu des fichiers .md).
- **Sur la carte du projet** : le nombre de tâches ouvertes (*3 à faire*), qui ouvre l'onglet ; rien quand il n'y en a pas.
- **Forgy** : un outil `project_notes` lit les tâches et les notes du projet (« qu'est-ce qui reste à faire sur ce projet ? ») ; ajouter ou cocher une tâche est une action qu'on valide, annulable.
- Rangé dans les données de DevForge (`project-notes.json`, par identifiant de projet), jamais dans le dossier du projet ; exporté avec les autres données (sauvegardes, export).

**Fini quand** une tâche ajoutée se coche, se retrouve comptée sur la carte, qu'une note en Markdown s'affiche mise en forme, et que Forgy répond à « qu'est-ce qui reste à faire ».

## Lot 2 — Alertes du CI GitHub

L'onglet GitHub lit déjà les workflows d'un projet. Les alertes le font en tâche de fond :

- toutes les 5 minutes, pour les **projets favoris** liés à GitHub (avec le jeton de GitHub CLI ou celui des Paramètres), le dernier passage de chaque workflow ;
- un workflow qui **passe d'un succès à un échec** déclenche une **notification de Windows** (le projet, le workflow, la branche) ; un clic ouvre l'onglet GitHub du projet ; un échec déjà signalé ne l'est pas deux fois, un retour au vert est signalé une fois ;
- sur la carte du projet, un **point rouge** tant que le dernier passage est en échec ;
- **Paramètres › Général** : *Alertes du CI GitHub* (activé par défaut, désactivable), et seulement les favoris ou tous les projets ;
- peu d'appels : une requête par projet, rien quand l'app est fermée, rien sans connexion GitHub.

**Fini quand** un workflow qui échoue sur un projet favori fait apparaître une notification et le point rouge, et que le retour au vert les fait disparaître.

## Lot 3 — Tableau de bord d'activité

Une page **Activité** (menu Développement), lue dans Git en local, sans service en ligne :

- **commits par semaine** sur tous tes projets, les 12 dernières semaines (un graphe en barres, une couleur par projet pour les plus actifs, le reste en « autres ») ;
- **les plus actifs** ce mois-ci (commits, lignes changées) et **ceux qui dorment** (aucun commit depuis 3 mois), avec la date du dernier ;
- **les branches à suivre** : des commits pas poussés, ou à récupérer, projet par projet ;
- filtre par dossier de projets et par auteur (toi seul, par défaut l'adresse de `git config user.email`) ;
- un widget **Activité** pour l'accueil (la semaine en cours, les branches à pousser).

Lu à l'ouverture de la page, six projets à la fois, gardé quelques minutes.

**Fini quand** la page montre les 12 semaines de commits de tes projets, un projet endormi et une branche à pousser, en moins de deux secondes pour une trentaine de projets.

## Lot 4 — Schéma de la base

Un bouton **Schéma** dans l'explorateur de base (page Base de données et onglet de la fiche projet) l'ouvre en plein écran :

- chaque table en carte : ses colonnes, la clé primaire 🔑, le type, *requis* ;
- une flèche par clé étrangère, de la colonne qui pointe vers la table pointée ;
- placement automatique (les tables liées côte à côte), puis tables déplaçables ; zoom, ajuster à l'écran ; la position est gardée par base ;
- un clic sur une table ouvre sa **Structure** ; la liste des tables à gauche les coche, les cherche, ajoute leurs voisines ; une mini-carte ;
- **Exporter** en image (PNG ou SVG) ;
- PostgreSQL, MySQL / MariaDB et SQLite ; au-delà de 60 tables, on choisit celles à montrer (et leurs voisines).

**Fini quand** le schéma d'une vraie base (une vingtaine de tables) se lit sans flèches croisées dans tous les sens, se réorganise à la main et s'exporte.

## Lot 5 — Mes modèles de projet

- Sur la fiche d'un projet : **Enregistrer comme modèle** — un nom, une description, ce qu'il faut laisser de côté (proposé : `node_modules`, `vendor`, `.git`, `dist`, `build`, `.env` et les fichiers `.env.*` sauf `.env.example`, les environnements virtuels) ; un aperçu de ce qui sera copié (nombre de fichiers, taille).
- Dans **Nouveau projet**, une catégorie **Mes modèles** à côté de React, Symfony… ; un modèle se choisit comme une technologie.
- À la création : la copie du modèle, le **nom du projet remplacé** là où il figurait (`package.json`, `composer.json`, `pyproject.toml`, `Cargo.toml`, titre du README), puis les étapes habituelles (dépendances, Git avec un nouvel historique, GitHub, ouverture dans l'IDE).
- **Paramètres › Modèles** : la liste, renommer, supprimer, mettre à jour depuis le projet d'origine.
- Rangé dans les données de DevForge (une archive par modèle) ; jamais de secrets : un `.env` n'est pas copié, un `.env.example` l'est.

**Fini quand** un projet enregistré comme modèle en donne un nouveau, renommé, qui s'installe et démarre, sans `node_modules`, sans `.env` et sans l'historique Git d'origine.

## Lot 6 — Documentation et vérification

- Pages du site (français et anglais) : notes et tâches, alertes du CI, activité, schéma, modèles ; les actions de Forgy.
- Vérifié sur de vrais projets : un favori dont le CI échoue puis repasse, l'activité de tes dossiers « Projet Perso » et « Projet CEFIM », le schéma d'une vraie base PostgreSQL ou MySQL, un modèle tiré d'un vrai projet.

**Fini quand** chaque nouveauté a sa page dans les deux langues et que les vérifications ci-dessus passent.
